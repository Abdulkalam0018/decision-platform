# Review and hardening log

After the first complete version (186 tests passing), an internal review pass went through the code against the
assignment requirements and used small reproduction scripts to try to break each guarantee. Each finding below was reproduced,
fixed, and covered by a regression test in `tests/test_hardening.py`.

| # | Finding (reproduced) | Fix | Regression test |
|---|---|---|---|
| 1 | Only missing-data errors were caught in branch conditions, rule preconditions and dependency request expressions. A type error (e.g. the bureau returns `score: null` and a branch evaluates `credit.score > 700`) produced a 500 and left the request `IN_PROGRESS` and the idempotency key `processing`; the retry worker then raised on it every tick and starved other requests | Every evaluation site catches all exceptions and traces them; a containment boundary in `engine._execute_stage` turns any unexpected handler or adapter error into a committed, explained manual review; the worker isolates each request and records `worker.error`; the CLI worker loop survives errors | `test_branch_type_error_is_contained_and_explained`, `test_precondition_type_error_is_traced_as_error`, `test_dependency_request_expression_error_routes_on_error`, `test_unexpected_adapter_bug_becomes_manual_review`, `test_worker_continues_past_a_poison_request` |
| 2 | Dry runs used the production dependency hub: they counted side effects and, during an outage, opened the shared circuit breaker so the next real request was parked | Dry runs get a fresh sandbox hub (or recorded responses) | `test_dry_run_does_not_touch_production_dependencies` |
| 3 | Sandbox DoS: quadratic `sum` of lists (minutes), `'%0100000000d' % 1` (100 MB), ReDoS `(a+)+$` (12 s on 28 chars), regex pattern taken from input | `sum` numbers only, `%` on strings refused, concatenation capped, evaluation step budget, regex must be a literal or a parameter validated at load (compiles, length, no nested quantifiers), regex input length capped; Hypothesis fuzz test | `test_runtime_resource_guards`, `test_compile_time_rejections`, `test_step_budget_bounds_evaluation`, `test_fuzz_interpreter_is_total_and_bounded` |
| 4 | Tamper detection only covered audit rows; a forged `requests.status`/`decision` passed verification | `verify_audit` cross-checks each request's status and decision against the last audited transition and decision; reviewer decisions are now also audited as `decision.made` with the full decision | `test_forged_decision_in_requests_table_is_detected`, `test_forged_decision_payload_only_is_detected`, `test_reviewed_decision_verifies` |
| 5 | Compiler accepted: remote `$ref` (500 on every submit), invalid regex, wrong function arity, typos in reason placeholders (customers would see `<missing>`), duplicate-check fields not in the schema (silently disabling duplicate detection), `is` with numbers | All are compile-time errors now | `test_remote_schema_ref_rejected`, `test_regex_parameter_validated`, `test_reason_placeholder_typos_rejected`, `test_reason_placeholder_data_flow_checked`, `test_duplicate_check_field_must_exist_in_schema`, `test_compile_time_rejections` |
| 6 | Circuit breakers were keyed by adapter type, so the first workflow's thresholds silently applied to all | Keyed per `workflow:dependency`; thresholds update with new versions | `test_breaker_thresholds_honoured_per_workflow` |
| 7 | Rejected-intake audit stored jsonschema messages, which echo submitted values (emails, ids) despite the "hash only" claim | Audit stores field path and violated keyword only; the client still receives full messages | `test_rejected_intake_audit_contains_no_submitted_values` |
| 8 | HTTP edge cases: malformed YAML and a bad `evaluation_date` gave 500; `600000` vs `600000.0` under the same key gave 422; retrying an identical review gave 409 | 422 for malformed definitions and dates; fingerprint normalises numbers; identical review retry returns the same result | `test_http_malformed_yaml_and_bad_date`, `test_malformed_yaml_is_a_validation_error`, `test_bad_evaluation_date_is_input_error`, `test_numerically_equal_payloads_share_a_fingerprint`, `test_review_retry_is_idempotent` |
| 9 | Idempotency lease was a fixed 30 s and never renewed, while a single stage could legally run longer; a takeover could run concurrently with the original and a frozen `IN_PROGRESS` snapshot could be stored as the key's final answer | Lease derived from the workflow's worst-case stage time and renewed at every checkpoint; resumers claim the request with a CAS; keys complete only when the request is settled (otherwise 202) | `test_lease_is_renewed_while_request_makes_progress`, `test_two_resumers_cannot_both_claim` |
| 10 | Requests that ended `FAILED` counted as business duplicates, blocking resubmission after a technical failure | `FAILED` excluded from duplicate detection | `test_failed_request_can_be_resubmitted` |

The review also found documentation that overstated what the code did. Those sections of
[ARCHITECTURE.md](ARCHITECTURE.md) were corrected (error containment, dry-run isolation, breaker configuration, data
minimisation, tamper-detection scope), and the remaining limits are listed under "Known limitations" in
[TRADEOFFS.md](TRADEOFFS.md#known-limitations).
